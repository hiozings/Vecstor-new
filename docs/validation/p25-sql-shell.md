## 工作流与正确性

真实伪终端运行项目 CLI，通过真实 localhost gRPC 执行 `.open`、`.datasets`、`.import`、多行 CREATE TABLE、多语句 INSERT/SELECT、UPDATE 元数据与向量、向量距离别名查询、DELETE、切换另一个数据库和 `USE demo` 返回原库。字符串中包含中文、分号与转义单引号。

终端工作流结束后的预期行由手工给出，并通过 SessionClient 读取验证：

```text
[1, '论文;已更新', 12.0, [0.0, 0.0]]
[2, "书籍'引号", 5.0, [2.0, 0.0]]
```

针对零查询向量的结果为 ID `[1,2]`、平方距离 `[0,4]`。另验证 `1152921504606846977` 在 SQL、RPC、数据库重启之间没有被浮点中转截断。

导入数据采用独立保留的 Dataset 与 P1 LocalEngine 对照，固定非零查询向量 `[0.25,-0.5]`，覆盖全体、半数、单条、类别和空结果五组；ID 与距离逐项一致。它不是只比较返回条数。

重启操作状态测试使用终端工作流之后的命名无变化 UPDATE `shell-acceptance-restart`，单独验证持久操作日志；不将该探针冒充终端自动生成操作 ID 的提取结果。

## 测试与审查修复

新增测试覆盖 SQL AST 支持/拒绝、通用结果类型、事务回滚、不同数据库会话、持久提交/失败摘要、操作重试、旧读租约在 UPDATE/DELETE 后保持一致、到期/重启失效、协议错误、实际 PTY 快捷键和补全。

经过独立模块审查及整体审查，已修复并通过回归：

1. 超时只取消 Future 却让数据库线程继续工作：增加精确活动连接中断、取消事件和每 256 行读取的期限检查，验证超时后新查询可继续执行。
2. 失败 operation_id 可换 SQL 复用：将失败摘要和状态也持久记录，重启后仍拒绝不同请求复用。
3. 结果流行宽未与 schema 校验：缺列/多列响应现在明确报错。
4. 列名补全缺失和切库残留：按 DESCRIBE 实际行提取表/列，完整刷新替换缓存；选库失败保留原缓存。
5. 导入响应丢失后源文件移走使重试失败：先根据逻辑请求查操作日志，已提交导入直接返回原结果，源文件无需继续存在。

所有修复均先复现失败再验证通过，最终全套 319 项通过。P1/P2 的原回归保持可用。

## 环境与范围

新增 prompt-toolkit 3.0.53、Rich 15.0.0；Conda 预解析没有 UNLINK，原 Faiss、CUDA、NumPy 等版本不变。项目 console-script 以无依赖解析、无构建隔离的 editable 方式注册，环境声明和精确包清单已更新。

这是同机 TCP、真实终端、事务持久化与内核文件隔离验收，不是跨物理机器或性能测试。仍不支持 JOIN/复杂子查询、用户显式事务、任意外部文件 SQL、客户端上传、ANN/GPU 业务优化或 TLS/鉴权。普通 SELECT 目前在存储内存中物化后分批传输，向量表写入做完整校验；这些性能改进不作为本阶段完成内容。

普通启动不施加 Landlock；只有明确启用隔离模式才具有已验证的文件权限限制。读写数据库始终仅由存储服务拥有，选择数据库是每客户端状态。
