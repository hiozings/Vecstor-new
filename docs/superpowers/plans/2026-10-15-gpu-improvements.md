# GPU 索引计算后续改进计划

> **For agentic workers:** Use superpowers:executing-plans after user approval, with failing tests before behavior changes. Conditional research stages require evidence before expanding production scope.

**Goal:** 修正GPU边界语义，识别并消除可避免的端到端开销，在质量和完整性可比的前提下形成明确的GPU适用范围，再逐步扩展能力。

**Architecture:** 保留CPU基线、GPU单owner资源及存算隔离；优化会话/控制面/调度，按完整快照与参数组织批次。恢复与持久化纳入P4统一版本架构。

**Tech Stack:** 先复用Conda、Faiss、SQLGlot、gRPC、NumPy和现有NVML接口。新后端/依赖只在独立探测证明必要后评估。

**Spec:** [现状与问题分析](../../design/gpu-improvement-analysis.md)。状态：2026-10-15已获授权实施G0→G1→G2，代码及验收已完成：565项回归、1万行真实GPU隔离、两轮各54000请求对照；收口见文末。G3—G5未实施。

## 全局约束与验收口径

- 默认CPU exact不变；明确GPU请求不得静默改CPU，DATA_LOSS/取消/deadline不能被吞掉。
- CPU float64距离和距离/id排序作为真值；GPU ANN、CPU回退、纯GPU失败分别统计。
- 同一查询/批次的每个成员必须拥有正确快照、读租约、质量配置和资源引用；不同版本不能混批。
- 原60组结果保留；新调参使用新校准/留出划分，不能利用已看过的500条留出反向择参后继续称独立评估。
- 质量目标仍为适用组平均Recall@10≥0.95，另要求合法数量充足的请求不能以不足K的成功结果返回；不足K须有完整性证明。
- 不承诺GPU普遍提速或超内存检索。GPU资源/设备数/权限由本机检查确定，不修改base或驱动。
- 用户已授权提交既有分析文档并创建改进分支；当前codex/gpu-improvements，不自动合并/推送。

## Review Focus

1. 已穷尽全体候选与“本轮没找到更多”不可混淆。
2. 旧服务、重启、连接复用后不得忽略设备/质量请求；写控制不能因能力缓存误操作CPU索引。
3. 合批中取消一个请求不得污染其他结果；index/lease引用不得提前释放。
4. 热会话/新连接、后端公平对比/产品真实体验必须分别报告；不要把控制面开销当kernel性能。
5. GPU覆盖扩展不能通过截断预算、污染留出集或计算CPU回退结果达成。

## Task 1：G0 修正边界语义与完整性校验（第一轮，必须先做）

**Files:** compute/vector_execution.py、index/gpu_backend.py、gpu_worker.py；tests/integration/test_gpu_execution.py、tests/unit/test_gpu_integrity.py与test_gpu_worker.py。
**Interfaces:** 执行计划新增 `candidate_space_complete` 与明确的穷尽停止原因；GPU响应解码统一产生严格类型的候选或GpuDataError。

- [x] 写失败回归：1024行/nlist1/全量L，WHERE分别命中0、1、K-1条，严格GPU均应返回全部合法结果且不转CPU。
- [x] 实现完整覆盖证明：同快照、全部唯一ID成员验证、已验证候选总数覆盖完整候选空间。未覆盖时继续扩展或按原严格策略失败，不能用nprobe=nlist单独证明。
- [x] 写失败回归：浮点/布尔/字符串ID、int64溢出、错误帧身份/长度/统计NaN；启用device_fallback=cpu仍应DATA_LOSS。
- [x] 在转换前做类型与范围校验；区分设备不可用和协议损坏，保留已有native非有限结果修复。
- [x] 定向复现CPU/GPU不同nlist的回退、EXPLAIN计划与实际策略、清理/期限交错。确认缺陷才修，不将猜测直接写成已修复事项。
- [x] 验收：两项已复现问题消失，原不完整大表请求仍失败；完整回归及真实GPU/隔离通过。更新错误说明与日志。

## Task 2：G1 建立可信成本基线并减少重复控制面调用（第一轮）

**Files:** rpc/sql_client.py、compute/sql_service.py、compute/service.py、index/gpu_worker.py、rpc/timing.py、新增benchmarks/gpu/sessions.py；新增针对会话复用与计时口径的测试。
**Interfaces:** 能力缓存仅用于可安全缓存的只读查询；响应设备/质量确认保留。计时字段明确client-preflight、server-admission（能可靠测得时）、GPU排队/IPC/执行及数据RPC，不强行填未知值。

- [x] 测试新会话GPU质量请求只获取一次必要能力信息；热会话复用，服务切换/旧服务响应仍被拒绝。构建/清理不复用可能过期的只读能力缓存来省略安全确认。
- [x] 去重GetSearchCapabilities与list_quality_profiles；明确缓存失效和服务身份。保留完成帧确认，禁止仅凭缓存接受GPU成功。
- [x] 基准每个并发客户端复用自己的连接、选库及配置；新连接负载另列。相同SQL设置、质量检查方式与参数用于纯后端对比，另测默认CPU对显式GPU的产品体验。
- [x] 将接入/控制RPC与存储RPC计数分开；独立GPU排队与IPC计时。只有能正确绑定Faiss实际CUDA stream时才增加事件计时，否则kernel/H2D/D2H保持null。
- [x] 选代表性的规模/选择率/K/并发1、4、8组，每组至少3次独立重复、累计≥1500请求；冷克隆、热查询分开，记录种子、机器负载、置信区间。
- [x] 验收：原始与新基线口径可解释；用证据确认主要耗时后进入G2，不先假定GPU队列或内核是瓶颈。

## Task 3：G2 有界合批与数据路径优化（第一轮，按G1结论选择）

**Files:** index/gpu_worker.py、gpu_backend.py、compute/vector_execution.py；如RPC瓶颈确认，再改lease_io.py、storage/sql_service.py及v2 proto并生成代码。
**Interfaces:** 一个批任务带多个独立request_id；按完整IndexKey、worker generation、device、precision、nprobe和候选L分组。初始探索batch上限1/4/8，等待窗口0/0.5/1ms，可单独关闭。

- [x] 先验证Faiss批搜索对不同查询的候选一致性、顺序和int64 ID；只合并兼容参数，不为凑批扩大某请求的预算。
- [ ] 建立批内独立状态、期限、取消和结果拆分测试；最早deadline不足时立即派发。正常取消丢弃该成员结果，索引物理引用须保留到实际计算完成；真正设备故障/硬看门狗超时才失效worker。
- [ ] 保留单owner资源，不能让多个Python线程直接共享GPU Faiss对象。对计算服务线程池拥塞，仅在G1确认后调整准入/异步等待，不盲目增加线程占满存储扫描名额。
- [x] 若RPC确认是主要开销，实验合并候选过滤与合法向量获取：保持同一租约、逐ID存在性/顺序/完整性检查、消息/批次上限、4扫描名额及总deadline。不能一次返回超大向量消息。
- [ ] 若IPC序列化占比显著，再替换查询/结果数组的JSON为有类型的二进制帧；优先保持匿名管道。共享内存只在有实测必要性后单列生命周期与隔离设计。
- [ ] 验收：合批开关前后每个请求的过滤、距离、预算与质量不变；取消不损坏邻近请求。报告吞吐和P50/P95退化场景，仅对实测有收益的负载启用。

## G3：显式自动设备/路径选择（第二轮，与P4策略统一）

**Files:** query/search_options.py、quality_policy.py、compute规划模块、EXPLAIN/终端与协议；新增策略边界测试。
**Interfaces:** 拟新增 `device='auto'`，必须由用户显式选择；决策输出目标设备/路径、理由、证据范围与实际回退。CPU/GPU质量配置独立匹配，不跨后端复用证据。

- [ ] 先用G1/G2数据建立可解释规则：支持性/质量/预算优先，再考虑数据量、通过率估计、候选需求、队列深度及克隆状态。
- [ ] 未知范围采用明确的保守策略，不能把样本候选通过率冒充全表选择率；统计采集成本计入计划。
- [ ] 测试显式cpu/gpu不被auto覆盖，严格模式不会偷偷降级；没有匹配质量证据时不能宣称Recall保证。
- [ ] 验收：已知退化组可解释地避开GPU，真正GPU适用组保留收益；同质量比较固定CPU、固定GPU和auto，不以CPU回退抬高纯GPU成功率。

## G4：资源、恢复与持久版本维护（与P4合并实施）

**Files:** index/gpu_registry.py、gpu_worker.py、compute/index_manager.py；存储索引工件/版本清单和分发协议由P4设计共同确定。
**Interfaces:** 资源账本区分CPU常驻/克隆临时量、GPU常驻/scratch/context；持久CPU索引工件带快照身份、构建指纹、校验和。GPU副本仍可重建。

- [ ] 增加多副本、反复清理/克隆、外部显存占用、故障/取消后的资源实测；设置主机与设备预留，审计清理等待是否越过调用期限。
- [ ] 区分用户取消、队列超时、native调用超时和设备故障；将正常取消影响限制到单请求，真正故障保留整个generation失效。
- [ ] 由存储侧发布完整且已验证的CPU索引工件，计算侧通过RPC加载并克隆GPU；无共享目录读取。重启恢复/预热必须显式配置，不能暗中训练。
- [ ] 批量更新原子发布新版本，旧读引用结束才回收；表级版本优化须与数据库revision及旧配置兼容一起设计，不能只删除版本校验。
- [ ] 两个计算节点验证版本一致性、损坏工件拒绝、失败发布回滚和重启加载。更新后的质量配置重新验证/绑定，不直接修改旧profile身份字段。

## G5：GPU覆盖扩展可行性实验（条件阶段）

**Files:** 新增独立benchmarks/gpu扩展探测与报告；不先替换现有后端。
**Interfaces:** 对照输出GPU路径、实际候选覆盖、Recall、完整性、传输/显存/构建成本；失败与CPU回退单列。

- [ ] GPU先过滤比较：验证真正过滤/掩码后端或显式过滤分区；临时子集搬运可作研究对照，但查询时构建临时索引须另行批准并显式展示成本。
- [ ] 大候选比较：CPU先过滤/回退作为实用基线，GPU物理分片或分块扫描作为实验。证明局部候选充分性，禁止“每片L/S”或重复Top2048伪分页。
- [ ] 对原24个未通过/不支持场景使用新校准/留出集合评估，清楚区分“服务能借CPU完成”和“纯GPU覆盖扩展”。
- [ ] 只有质量、完整性、资源和端到端成本满足目标才产品化；不满足则保留边界和CPU策略，不把试验失败包装成支持。

## 延后功能

GPU训练、GPU Flat对照、FP16/PQ、多GPU分别单列设计，不要求本轮一并完成。GPU训练只有构建阶段实测值得优化时推进；FP16/PQ必须重新校准；GPU float32全扫描不能改名为原float64 exact。当前没有证据要求增加显卡、改驱动或升级Faiss。

本轮按授权实施 **G0 → G1 → G2**，交付修正后的完整性语义、可信热会话基准、去重复控制调用和经验证有收益的合批/RPC优化。G3根据新数据决定，G4纳入P4，G5作为独立研究。每个阶段先写失败回归、再实现、验证和更新文档；阶段结束保留原始结果及不成功场景。

最初分析阶段仅做两项补充探测；后续已进入获授权的实施阶段，完整记录见 [改进验收](../../validation/gpu-improvements.md)。

- 分支与目录：复用当前工作目录并创建用户要求的新分支，既有分析提交f7840b1；用户.gitignore保持不动。没有额外worktree，代价是需要继续注意用户并行修改。
- 计划工具将G0/G1/G2映射Task1/2/3，G3—G5未纳入本轮；这只是记录编号变化，未改变ANN数学参数。
- G0原基线513通过/1失败，确认死worker就绪复用存在竞态。补native确认与确定性回归，保存原失败日志。生命周期调度重构原拟结合G2，最终按下面实测裁决延期，活动取消仍可能影响整个worker。
- G1采用三类代表负载、并发1/4/8、每组500不同查询×三次，CPU/GPU使用相同冻结参数；旧新建客户端短实验分开报告。代价是结论不覆盖原全部60组或真实业务分布。
- G2 native batch1/4/8一致性已验证；运行时合批、等待窗口、批内取消与异步调度未上线。因native占比低/GPU队列短而优先合并RPC，代价是可能错过少量native吞吐收益。上面的未勾选批调度条目是明确延期，不是已完成。
- IPC二进制/共享内存延期：现有测量未显示其为主要成本；保留匿名管道及严格帧校验。代价是原JSON开销仍在。
- 合并RPC有退化负载，默认关闭并提供SQL覆盖；超大元数据允许有记录的mixed传输。代价是用户需按负载选择，未提供自动策略。
- 审查的两项Important均纳入一次修复：普通CRUD错误要求向量路径/设备确认；队列满时复用检查错误重置健康worker。前者可导致已提交写入被误报失败，属于必须修复的高影响问题。回归先失败后修复；最终测试结果见验收记录。
- 审查未判断项裁决：批内取消按上文延期；G3—G5/P4不属本轮，版本持久化仍缺失；正式G2收益仅在完整实验结束后发布；既有活动取消回收worker保留并明确限制。代价分别为缺少单请求取消隔离、重启需重建、不能提前宣称提速、取消可能干扰其他GPU请求。新增队列满重置问题不在该延期范围。
