# GPU 索引计算现状、问题与改进方向

日期：2026-10-15。本文保留改进前分析；G0—G2后续实施状态见文末链接。原分析阶段未修改业务代码。基于当前实现、514项既有回归记录、正式校准和最终RPC实验，以及本次小规模补充探测；既有测试通过不代表下面的新边界行为已修复。

## 1. 当前实际能力

已经具备：SQL SETTINGS逐请求选择CPU/GPU、CPU训练后显式克隆GPU IVFFlat、GPU search-first、候选扩展、CPU float64重排、版本/读租约、GPU预算与有界队列、worker故障回收、显式设备回退、后端绑定质量配置及真实PTY/Landlock验证。

此前独立审查发现的native对象引用滞留、非有限结果错误分类、旧服务设备控制忽略、排队取消占容量等问题已修复，不列为当前未解决缺陷。

尚未具备：GPU先过滤、GPU训练、GPU查询合批、自动设备/路径选择、持久索引分发及更新维护、多GPU、半精度/压缩后端。CPU精确基线与重排保留是当前设计选择，不是“GPU实现失败”。

## 2. 已确认的质量与覆盖限制

证据：`results/gpu-calibration-20261015/report.json`。

| 范围 | 通过 | 不支持 | 留出失败 |
| --- | ---: | ---: | ---: |
| K=10，共30组 | 19 | 8 | 3 |
| K=100，共30组 | 17 | 13 | 0 |
| 合计 | 36 | 21 | 3 |

通过组最低平均Recall@10=0.9608、Recall@100=0.97032。21个不支持组中，18组属于2048候选限制/校准质量完整性条件无法满足，3组属于真值少于K而工具未提供纯GPU完成路径。不能把21组全部归为GPU硬件不支持，也不能把36/60解释为单查询成功率。

3个留出失败组的平均Recall分别为0.999、0.9686、0.9974，但存在1、7、1条结果不足，共9条。**平均召回合格与每条查询结果完整是不同指标。** 当前不导出这3组质量配置是正确行为，不能通过隐藏失败、算入CPU回退或在同一留出集重调参数“修复”实验。

本机安装版本实测：一次GPU检索的候选L及nprobe≤2048，IDSelectorBatch参数虽被接受却没有正确过滤。因此低通过率先检索容易耗尽候选，且不能把现有CPU selector直接搬到GPU。该2048边界针对当前后端与版本，不是所有GPU算法的永久上限。Faiss官方亦说明当前标准GPU实现的相关限制：[GPU说明](https://github.com/facebookresearch/faiss/wiki/Faiss-on-the-GPU)。

## 3. 本次新增、可复现的边界问题

证据：`results/gpu-improvement-analysis-20261015/probes.json`。本次启动临时存储/计算服务和真实GPU，结束后清理服务与临时数据库；未改用户数据。

### A. 完整候选空间已覆盖，仍不能返回空集或不足K的合法全集

1024行、nlist=1、nprobe=1，L与预算均为1024；查询LIMIT10，分别筛选0条和1条合法记录。CPU精确查询返回 `[]` 和 `[[209]]`，GPU均返回 `FAILED_PRECONDITION: gpu_exact_fallback_candidate_budget`。

原因：执行器把 `matched < K` 一律送入回退，即使已经取得并验证整个索引快照的全部唯一ID。应区分“预算耗尽但仍有未知候选”和“候选空间已完整穷尽”。后一种情况可直接返回已找到的全部合法记录，不需要切CPU精确模式，也不需要新增GPU精确内核。

修复必须以同租约、正确版本、全部ID经过校验且覆盖数等于完整候选空间为证明。仅“这一轮没有新结果”、返回不足L或nprobe=nlist均不足以证明完整覆盖。大表超过候选上限时仍不能据此返回不完整成功结果。

### B. GPU响应ID存在隐式类型转换

`GpuIndex.search` 在校验前执行 `np.asarray(..., dtype=int64)`。对错误worker响应 `ids=[1.9]`，当前实际接受为 `[1]`，只要1存在于快照中便通过后续成员校验。

这是故障/损坏响应的完整性风险，不表示正常SQL输入会让ID变成小数。应在转换前严格拒绝float、bool、字符串、超int64范围值，统一使用DATA_LOSS且禁止CPU回退。同步审计帧长度、版本、generation、统计值与错误分类，避免相同模式遗漏。

## 4. 性能不足及更准确的归因

证据：`results/gpu-rpc-reviewed-20261015/`；汇总：`results/gpu-improvement-analysis-20261015/cost-summary.json`。每个对照组只有9次查询，下面是描述性结果，不是统计显著性结论。

| 并发 | CPU/GPU匹配组数 | GPU P50更低的组数 | 各组GPU/CPU P50比值的中位数 |
| --- | ---: | ---: | ---: |
| 1 | 36 | 9 | 1.179 |
| 4 | 36 | 3 | 1.402 |
| 8 | 36 | 0 | 1.904 |

这说明当前GPU实现尚无普遍端到端优势，但不能据此认定GPU检索内核慢。

例如10万行独立分布、100%通过率、K10、并发1：CPU faiss_search_ms中位数3.72ms，GPU包含IPC的faiss_search_ms为2.12ms，其中gpu_host_ms为0.77ms；RPC等待分别18.37/24.98ms。GPU检索环节更短，整体查询仍可能更慢。以上各阶段独立中位数不能直接相加当作同一条查询。

并发8时同组GPU的客户端耗时减compute_elapsed_ms，中位差约100.82ms；CPU约28.22ms。这一差额包含控制面RPC、客户端解析/编码、网络和计算服务进入执行器前的等待，**不能全部归因于GPU队列**。当前计算服务只有4个RPC工作线程，值得补测接入排队；不能未经测量就简单增加线程，更不能让多个线程共享Faiss GPU资源。官方线程约束见 [Faiss线程说明](https://github.com/facebookresearch/faiss/wiki/Threads-and-asynchronous-calls)。

已从代码确认的额外开销：

- 每次GPU查询调用GetSearchCapabilities；新客户端若还使用quality_profile，又通过list_quality_profiles重复获取一次能力信息。
- 现有成本工具在每次请求内新建SessionClient并重新选库，未反映交互终端长期复用会话的主要用法。GPU配置路径与CPU显式参数路径的控制面成本不同，不能将全部差异解释为后端差异。
- 单owner worker逐条检索，没有利用Faiss的批量查询接口；单查询JSON编码、匿名管道、host/device传输存在固定成本。
- FilterCandidates与FetchVectors串行执行，数据RPC开销仍占较大部分；候选越多成本越大。
- gpu_ipc_queue_ms混合了排队、IPC、编码和父端等待；kernel/H2D/D2H尚无独立可信测量。

因此优先顺序应是：完善测量 → 去重复握手/复用会话 → 再评估合批与RPC优化。Faiss官方指出批查询通常更适合GPU，但这不构成当前引擎的加速承诺：[GPU性能说明](https://github.com/facebookresearch/faiss/wiki/Faiss-on-the-GPU)。

## 5. 资源、可用性和维护不足

| 现状 | 影响 | 改进方向 |
| --- | --- | --- |
| GPU逻辑字节沿用CPU序列化大小，另做free memory预检 | 不是实际驻留/峰值，临时缓冲和外部占用可能导致预估误差 | 分开统计CPU副本、序列化/反序列化、GPU索引、scratch/context和预留；审计克隆阶段峰值 |
| 512MiB逻辑预算≠VRAM硬限；GPU worker采样RSS曾达619.1MiB | 用户容易把GPU加速理解为减少主机内存 | 展示完整主机+显存账本及采样范围，不做硬限承诺 |
| 活动请求取消/超时会杀整个worker | 无关排队请求失败，全部GPU副本需重建 | 区分请求放弃与设备故障；正常完成后丢弃取消请求结果，真正失控才重置设备 |
| 所有GPU操作共享一个owner队列 | 长克隆/资源回收可能阻塞短查询 | 测量控制/查询排队，设置明确准入和调度规则；保持资源线程安全 |
| 每次重启需CPU准备并GPU克隆，写入使数据库级revision改变 | 重建开销、其他表写入也保守失效；配置维护频繁 | 与P4统一做CPU索引持久化/发布/恢复及表级版本设计 |
| 质量配置绑定精确快照、SQL范围和GPU型号 | 保证保守，但正常用户需要大量手工重校准/绑定 | 支持用户数据/查询集、可解释的配置失效原因、显式重绑定工具；不绕过版本校验 |
| procfs权限范围较宽，默认无TLS/鉴权 | 只适合可信环境的存储文件隔离 | 容器/独立用户/设备授权作为部署强化；不能宣称已有恶意同用户隔离 |

代码审计还发现需定向测试的风险：设备回退时CPU/GPU可能使用不同nlist；EXPLAIN的回退描述与严格GPU策略可能不完全一致；超长/损坏IPC帧的错误分类、清理等待与请求deadline交错需要系统验证。这些暂列待验证风险，不冒称已复现的生产故障。

## 6. 待实现功能的优先级

**下一轮优先：** 两项边界修正、完整性/失败原因展示、热会话基准、控制面去重、分阶段计时，以及有界查询合批的实验与实现。

**随后按证据推进：** 显式device=auto、CPU/GPU路径选择，GPU负载准入/取消隔离，候选过滤与向量获取的合并RPC及有界缓存。这些与P4策略/缓存工作合并设计，避免重复接口。

**需要独立可行性门槛：** GPU先过滤、超过2048候选的大集合查询。当前不支持掩码的后端不能假装支持；可比较支持过滤的后端、显式构建的过滤分区，以及临时子集搬运的成本，但不直接升级依赖或偷偷引入查询时建索引。

**与P4统一交付：** 持久化CPU索引工件、完整版本清单/校验、重启加载并克隆GPU、批量更新发布、旧读引用保留、两个计算节点一致性。GPU内存对象本身不是权威持久数据。

**低优先级可选：** GPU训练、GPU Flat对照、FP16/PQ、多GPU。先测出构建或容量瓶颈再选；GPU训练会改变训练指纹/质量证据，FP16/PQ涉及精度与召回，GPU float32全扫描也不能直接替代现有float64精确契约。

## 7. 大候选方案必须避免的错误

重复相同GPU Top-2048查询不能得到“下一页”。简单把全局L按分片数量平分，再取每片L/S也不能保证全局候选完整，因为近邻可能集中在一个分片。

如研究物理分片，应验证共享粗量化器/ID/版本关系、局部候选充分性、合并规则和总预算；需要局部L>2048时，仍要有可证明的细分/扫描方案。把每片限制到可全部枚举的大小可绕开单次输出上限，却可能造成大量kernel调用和传输，必须先做独立成本实验。不能把分片天然视为更快，也不能用CPU回退结果宣称纯GPU覆盖已扩展。

## 8. 推荐推进策略

先做兼容的小步修正与性能归因，再优化已支持的36个质量组。对原24个未通过/不支持组，先提供清楚的支持矩阵和显式CPU先过滤/精确回退方案；纯GPU覆盖扩展单独验证。性能验收同时约束召回、完整性和回退率，不承诺预设加速倍数。

对应分阶段执行计划见 [GPU改进计划](../superpowers/plans/2026-10-15-gpu-improvements.md)。
